# Menu motion regression harness

`MotionSequenceTests` runs in the debug app test suite. `MotionFrames` hosts the production Models and Activity item views in borderless windows at (-9000, -9000), never ordered on screen. Storage must be isolated with `ARSENAL_SUPPORT_DIR` and `ARSENAL_CACHE_DIR`; skip `SingleInstanceTests` when running the app suite. No model or download is needed: row states and Activity feeds are fixtures, and native row action presses use a counting sink.

First-frame tests cover attachment after rows have arrived and Activity’s initially empty panel. The normal tests render the actual presentation layer into RGBA bitmaps. They sample the main run loop, layout and layer tree following each state change. No material stand-in or mock view is drawn. Nonanimated sequences must contain only the complete before or complete after image. Every sequence checks for blank content, opaque corner flashes, duplicate native button frames, stable surviving controls, and intermediate host sizes. The table also pins the unaffected neighbour's action/gear and Refresh by identity and exact frame. Activity's CPU/GPU label pixels and all endpoint-identical pixels outside its changing meters stay identical while its existing animations run. The meters must advance monotonically; their tiny initial antialiased caps are part of the changing control. Idle probes compare pixels and presentation geometry and count host layout/draw and native action, gear, Refresh and pinned-row draw passes; capture-driven drawing is excluded. The service event test counts reads and publishes, then verifies that reads stop at rest.

For evidence, set `ARSENAL_MOTION_STRIPS` to an output directory. This opt-in writes every sampled bitmap, four-frame strips (before, first sample, middle, final), and actual sample intervals plus layout/resize counts. Saving PNGs is slower than the normal suite. Transparent images retain their real alpha; a viewer that ignores alpha can make translucent white fills look opaque. Inspect alpha before calling such a fill a flash.

Coverage: Models open; Refresh hover/press/exit and disable/enable; row hover/press/exit; Get, Load, Unload and Reload presses; Get → downloading → Loading → loaded; busy presses refused; pending row; error footer appearance/removal; row insertion; the gear opening a model's settings card beside it (the table's size, allocation and every pixel outside the open row and the card unchanged on every sampled frame; the gear and the row's action keep their frames and identity), the gear pressed again and the card closing (the table back to its exact first pixels); the card's own frames (`theSettingsCardChangesInPlace`: first frame complete, a switch flipping in one step, the name line unchanged, Restore defaults keeping its frame and identity, the table's size and the card's frame unchanged, nothing drawing at rest); Activity request insertion, step/GPU updates, and completion; Activity one-second tick and queue drain (counts, minute, busy graph and the CPU/GPU meters switch in place with no eased frame, the drained queue keeps the card's height, the empty minute shrinks it once); identical row snapshots, unchanged Refresh availability, a menu closing with nothing open, and repeated service errors.

Limits: these are sampled, driven offscreen frames, not a WindowServer display-link recording. Sample intervals are recorded, not assumed to be the physical refresh rate. An unordered window cannot verify native NSMenu tracking, the WindowServer's translucent menu backdrop, actual display cadence, pointer tracking across menu boundaries, or screen-edge placement. The fixture keeps NSMenu's requested natural height when width is constrained and mirrors allocation after its item view changes size; it cannot prove that the real native menu window reallocates on the same compositor frame. Draw counters cover the hosting boundaries and four native control types; SwiftUI's private renderer does not expose an exhaustive per-layer redraw count. These limits must remain in review/install reports.

`MenuStabilityTests` covers window-dismissal ordering, all four tool kinds in both parent tracking states through HTTP and MCP, the recorded negative offsets in production Models/Activity hosts, provisional 10×10 windows, native action presentation and executable tool recovery. Visibility sequences retain unrelated menu items and both hosted views, comparing exact pixels/frames and the hidden status item's allocation after both visibility values. Only genuinely added/removed tool items change. Surviving native items retain their native view, highlight, checkmark and keyboard behavior; macOS may dismiss tracking when a native menu item is selected.

`MenuRound2Tests.nestedViewerRepairPreservesContainment` retains the production menu-item association and supplies two item-sized ancestors inside a 971×522 window. It tests flipped and unflipped ancestors at y=-80.5, then verifies the full 971×512 content is at y=5, contained by every ancestor, and reachable by hit testing. Repair moves the responsible displaced ancestor, rather than moving its child out of that ancestor. Ordinary height growth still waits for AppKit's allocation without publishing a smaller fit; displacement retains vertical containment after repair. The geometry log records invalid allocations before repair and flags provisional 10×10 windows.

`residentVoiceRecoveryNeverDispatchesUnload` exercises resident voices with changed code consent, with and without pending setup. Tool recovery explicitly dispatches Get or Load, including the existing plan bounds, revised-plan confirmation and digest-specific app approval. It never invokes the table's toggle, which would select Unload for a resident row. `MCPMenuPlacementTests` checks `arsenal_settings(model:…, set:{show_in_menu:…, …})`, which writes Show in menu and model settings in one atomic write: invalid booleans, unknown settings and invalid model values leave both unchanged. `MenuPlacementWriteTests` repeats that contract on the real service, verifies catalog invalidation and reopen persistence, and forces a persistence failure to verify full rollback. Placement is saved in selections, never sent to a runner as a model setting.

`SettingsCardTests` holds the invariants from the 13 Oct menu log, run on every build: a gear's mouse-down and mouse-up, through the table host's hit test, open and close the card with no action through the enclosing menu item and no cancelTracking, exactly as the row's Load button; every control of Qwen's, FLUX's and Kokoro's cards acts in place with the Arsenal menu and Models open, and the card closes on Esc, on a click elsewhere in the table (which does its own job), on another row's gear (its card takes the place) and with Models; Show in menu switched off and on for every catalog model with tools while the menus are open adds or removes no item in any open menu (zero didAdd/didRemove notifications, `structuralCalls` 0 in the close log) and the main menu follows once they have closed; the card never changes the table host's frame or the item's natural size and sits beside its gear inside the table for every catalog model; no `applies = "request"` setting appears in any catalog model's card; no `NSMenu.popUp`, NSPopUpButton or NSComboBox is reachable from the Models menu (source scan and the open cards' view trees). `ARSENAL_CARD_RENDERS=<dir>` renders Qwen's, FLUX's and Kokoro's cards in the user's table, dark and light. Limits: these drive AppKit's hit test and event methods directly in unordered windows; how real menu tracking routes the click, the mouse-up and Esc to the hosted table on screen, and how the behind-window material looks over a real desktop, remain unverified offscreen.

Round 2 adds: dismissal tied to the Models menu's session (a replay is void once Models closes, needs a live gear, and one token covers both delivery orders; a close by code or an event from before the open is no click; a late close of a replaced presentation is ignored), Esc/table/Arsenal-menu/outside clicks, the controller released after its settings close, ⌘A/C/X/V through the host's key equivalents, Return committing a one-line field without closing, drafts committed after the view is detached, per-model width (376–480 pt), the lock reason under the locked row, Restore drawn off at defaults, the parent row's neutral fill, the form scrolling past its room, and the header name level with the row name (ink measured within 1 pt). `LiveMenuCheck` (opt-in, lab profile only) is the live counterpart; its dry run is tested by `LiveMenuCheckTests`.

The old-settings audit uses the actual TableController paths. Keep loaded, Show in menu and ordinary model-setting writes have no cancellation handler. Precision, zero-byte Get, Load, Unload and Refresh are exercised through production hosted controls and do not call cancelTracking. The baseline source shows the old settings footer's Reload delegates to `reloadFromSettings → perform → start → confirmCode` when consent is needed; that callback dismisses for its NSAlert. The test exercises the footer's shared `perform` tail without depending on the removed form API. A file setting delegates to `chooseFile → pickFile`, which dismisses for NSOpenPanel. All five confirmation/file-picker paths now assert dismissal before their injected presenter is invoked. This corrects round 1's claim that those five calls were accidental dismissals from ordinary settings writes.

Evidence from the incident records bad allocation, not the clicked control or a tracking-end reason. An offscreen callback audit can prove those explicit window paths and rule out ordinary settings-write cancellation; it cannot establish which path ended the user's particular live tracking session. Root/tool replacement and displaced hosted allocations are reproduced regression inputs, not proof of that incident's initial tracking-end event. The settings-window lane removes the embedded form; its integration remains a separate review boundary.

The round-1 replay of the three new review regressions failed with 15 issues: nested containment/scale, resident Voice approval/recovery (the resident was unloaded), and MCP's unknown `__tools` setting. Replaying the relevant four menu production files from 2e0446f passed the cancellation audit and window-order test, while the three geometry tests failed with 19 issues. Those four production files were restored byte-for-byte afterwards.

These tests cannot verify live NSMenu tracking/dismissal, native backdrop or screen-edge placement, physical frame cadence, keyboard traversal, or a visible status item's WindowServer composition. Hidden/offscreen tests preserve the user's screen and prove object allocation, callback routing, hit testing and sampled frame stability. Real modal windows are not presented during tests; only their construction, dismissal ordering and return routing are exercised. Fresh coordinator review remains required before merge or installation.

Round 2 verification: the complete suite, excluding `SingleInstanceTests`, passed 804 tests (Core 387, API 72, Bench 2, App 335, RunnerCheck 8). After tightening Voice's pending-setup plan and correcting the fixture to retain the Operation tool instead of silently substituting Chat, the final affected run passed 11 test functions / 31 parameter cases. All builds/tests used `nice -n 10`, isolated storage and the lane's own build directory. No model runs, downloads, on-screen menus, merge or install were performed.

`MenuRound3Tests` records actual `NSMenu.removeItem`/`insertItem` calls on surviving native roots. Two loaded voices cover hiding and removing the first voice while the second Voice submenu is open; sampled Activity pixels, dimensions and control frames, and the surviving Voice submenu’s native requested size, stay unchanged. Native text-only item viewers are not instantiated by `NSMenu.size` without tracking; the sampled frame check therefore uses the production hosted Activity view, not a fabricated Voice viewer. A four-tool matrix covers hide/show/remove/add/catalog refresh, plus a reordered snapshot, duplicate model names, renamed model headers and an idempotent attached snapshot. All surviving items receive zero remove/insert calls. Playback controls now follow all model sections, and reconciliation retains attached survivor order across catalog changes.

`MenuCloseLogTests` exercises one close per open, all production menus and cancellation call sites (including the real gear press), real native item-action notifications after `menuDidClose`, including delayed delivery before the native tracking-end notification and a child tracking cycle ending before its parent, app resignation, current/stale/missing events, structural remove/reinsert cycles, original delegate forwarding and the existing bounded background writer. These are synthetic lifecycle callbacks and unordered windows: they do not claim an observed live dismissal, nor that `NSApp.currentEvent` is necessarily the event that ended AppKit tracking.
